# AI Health Steward 产品功能优化建议

> 基于真实环境端到端实测（数据库 / 后端 / 模型 / 前端渲染）+ 全量代码审查
> 配套文档：`review/功能测试问题报告.md`（缺陷明细与复现步骤）

---

## 一、产品判断：这个产品做对了什么

在给建议之前，先说清楚我看到的产品优势——后续建议都是围绕「把已有优势真正交付出去」展开的。

| 优势 | 说明 |
|---|---|
| **画像作为单一事实来源** | A-H 全字段族的设计是对的。多数健康 App 是「记流水账」，这里是「建人」。这是真正的差异点。 |
| **双入口分工清晰** | 「飞书收集 + WebUI 深管」是符合真实家庭场景的定位，尤其照顾了长辈只用飞书的现实。 |
| **1+X+Y 体检推荐逻辑** | 把体检从「套餐销售」变成「基于画像的推理」，且做了安全禁忌排查。这是有专业壁垒的功能。 |
| **临床级细节** | 采用真实危急值阈值（180/110、16.7）而非相对启发式；参考范围按年龄分档避免误判儿童。这说明作者懂医学口径。 |
| **成本意识** | 消除重复 LLM 调用、无更新直接输出缺省页——自部署用户会真实受益。 |
| **隐私边界清晰** | 本地存储 + 可选本地 LLM + 明确说明「哪些数据会发给 provider」。 |

**核心结论**：产品方向是对的，问题**不在功能数量，而在关键闭环的最后一公里没有接通**。下面是三个产品级断点。

## 二、核心诊断：三个产品级断点

### 断点一：闭环断在最后一公里——「报告入档」没有产出任何行动

**这是最严重的产品问题。**

产品核心叙事是：`拍照上传报告 → AI 结构化 → 入档 → 画像/趋势/待办`。

实测结果（详见测试报告 P0-5）：

```
上传一份含收缩压 205、空腹血糖 22.5 的报告并确认入档
  → 入库为 abnormal=False, critical=False, ref=[None,None]
  → 没有红色危急横幅
  → 没有生成任何复查待办
  → 从报告导入的用药不生成用药提醒
  → 从报告导入的慢病诊断不生成随访待办
  → 同一份报告确认两次，数据全部翻倍
```

**产品视角的影响**：用户完成了最费力的一步（拍照、等待解析、逐项确认），**却什么反馈也没得到**。首页看起来和没上传一样，待办列表也不会多一条。用户会得出「这功能没什么用」的结论，而实际上数据已经进画像了——**价值被静默吞掉了**。

对比手动录入一条血压：会判异常、判危急、生成待办、首页红屏。**两条入口的「重量级」完全不同**，而报告导入才是主打入口。

**建议**：
1. **修复入档计算**（服务端统一用 `resolve_reference_range` + `is_critical_value`，不信任 LLM 判断）
2. **补齐后置钩子**（调用 `handle_metric_recorded` / `handle_medication_added` / `handle_diagnosis_added`）
3. **加一个「本次入档变化摘要」确认页**——这是产品层面最有价值的补充：

```
✅ 报告已入档
   本次新增 12 项指标 | 2 项异常 | 1 项危急 ⚠

   ⚠ 收缩压 205 mmHg（危急，参考 <140）→ 已生成「尽快复查」待办
   ⚠ 空腹血糖 22.5 mmol/L（危急，参考 3.9-6.1）→ 已生成「尽快复查」待办
   ＋ 新增诊断：2型糖尿病（已生成随访待办）
   ＋ 新增用药：二甲双胍（已生成用药提醒）
   ~ 对比 3 个月前：总胆固醇 ↑ 1.2，建议关注

   [查看画像]  [查看待办]
```

把「已经发生的好事」显式告诉用户，是提升留存成本最低的手段。目前这个产品把一个强价值时刻做成了无声操作。

### 断点二：提醒没有触达通道——「提醒」只会存在，不会提醒

**这是最高杠杆的功能缺口。**

README 宣称三个能力：**「复测/用药待办提醒」**、**「健康小结定期自动触发」**、**「飞书渠道集成」**。

实测代码事实：

```
全后端搜索飞书主动发送调用：
  feishu.py:147,156,187,194,197,201,226,237,282   ← 全部是「回复收到的消息」

summary_scheduler.py 中的 feishu/send/push 调用：   （空）
task_service.py      中的 feishu/send/push 调用：   （空）
```

**没有任何主动推送**。后台调度器每天在跑、自动生成待办和周报，但这些内容**只在用户主动打开 WebUI 时才可见**。

**这才是真正的产品问题**：一个「提醒」系统如果不会主动触达，它就只是「备忘录」。而目标用户（关注父母健康的子女、慢病长辈）最需要的恰恰是**不用主动打开也能收到**。

更可惜的是，**所有基础设施都已就绪**：
- 飞书 WebSocket 长连接已在跑（`feishu_bot.start_all()`）
- 每个渠道已绑定家庭成员（消息归属已解决）
- 调度器已按周/月/年自动触发
- 待办已按危急/复查/用药/随访分类
- 已有卡片消息发送能力（`_send_card_sync`）

**缺的只是把「生成」和「发送」连起来。**

**建议（建议作为 V1.3 头号功能）**：

新增 `notification_service`，在三个事件点推送：

| 触发点 | 推送内容 | 时机 |
|---|---|---|
| 危急值入库 | 红色卡片「⚠ 检测到危急值：收缩压 205，请尽快就医」 | 立即 |
| 待办到期 / 即将到期 | 「今天有 2 项待办：复查血压、续配氨氯地平」 | 每日早晨 |
| 周期小结生成 | 「上周健康小结已生成：3 项异常，1 项改善」+ 摘要 | 周/月/年触发后 |

同时提供**推送开关与静默时段**（避免打扰）：设置页加「提醒推送：危急值实时 / 待办每日汇总 / 小结周期汇总」三档。

**产品价值**：这一步把产品从「一个需要主动打开的管理后台」变成「一个会主动关心你的健康管家」——**这正是产品名里「管家」二字的含义**。也是与普通健康记录 App 拉开差距的地方。

### 断点三：告警只增不减——告警疲劳会让真正的危急值被忽略

**实测事实**：
- 首页「危急值 N」按**全量历史**统计（`Home.tsx:59`，无时间窗、非取最新），一年前的一次危急血压会让首页**永久红屏**
- 没有任何「已知晓 / 已处理 / 忽略」操作
- 待办列表实测：录入 3 次相同危急血压 → 新增 3 条同标题待办；`title counts: [('尽快复查收缩压', 4), ...]`
- 待办接口排序把 `critical` 排到 `normal` **之后**（字符串降序）

**产品视角的影响**：安全告警的价值取决于**信噪比**。当首页永远是红的、待办永远清不完、危急项还排在后面——用户会学会**无视**这些告警。那一刻，整个危急值预警功能就归零了。

对一个健康产品来说，**误报导致用户忽略真报**，比不报更危险。

**建议**：
1. **首页只统计「最新一条」或「近 7 天」**（与 Dashboard 口径统一）
2. **加「已知晓」状态**：危急值横幅可标记「已知晓，正在就医」，标记后降级为普通提示但保留记录（不能删，要留痕）
3. **待办语义去重**：同一指标名只保留一条 open 待办；重复触发时**更新到期时间**而不是新增
4. **待办排序修正**：危急 → 逾期 → 今日到期 → 其他
5. **待办支持「稍后提醒 / 改期」**——只有「完成/忽略」两个选项，会逼用户用「忽略」来逃避，从而丢失跟踪

## 三、功能优化建议（分级）

### P0 — 建议优先做（决定产品是否被信任）

| # | 功能 | 理由 | 工作量估计 |
|---|---|---|---|
| 1 | **飞书主动推送**（危急值/待办/小结） | 见断点二。基础设施已就绪，是「管家」定位的兑现 | 中（1 个 service + 3 个调用点） |
| 2 | **报告入档闭环**（异常/危急判定 + 待办钩子 + 变化摘要） | 见断点一。主打入口的价值交付 | 中 |
| 3 | **告警生命周期**（最新/时间窗 + 已知晓 + 去重 + 正确排序） | 见断点三。保护安全功能的信噪比 | 小-中 |
| 4 | **修复导出与清除的完整性** | 导出漏手术史/疫苗史，清除漏 4 张表且不删文件，但文案说「所有健康数据已清除」——**信任问题**，且涉及隐私合规 | 小 |
| 5 | **数据录入范围校验** | 实测体重 -10、血压 99999 可入库并触发「危急值请尽快就医」——误报会摧毁告警可信度 | 小 |
| 6 | **量表结果页补齐安全提示** | PHQ-9 自伤题阳性返回「状态良好」（详见测试报告 P0-3）——**临床安全 + 品牌风险** | 小 |

### P1 — 该做（显著提升可用性）

| # | 功能 | 现状问题 | 建议 |
|---|---|---|---|
| 7 | **首次使用引导（Onboarding）** | 无成员时 Chat/Reports/Dashboard/Summaries/Assess **全部**只显示「请先选择家庭成员」，只有首页引导去创建。新用户第一印象是「一堆空页面」 | 三步向导：① 创建第一个成员（含身高体重必填）② 配置模型（含连通性测试）③ 二选一入口引导（绑定飞书 / 上传第一份报告） |
| 8 | **体检推荐问卷流程重构** | 实测需逐条回答 11 项安全禁忌，每项三选一（是/否/不详）；移动端近 33 次点击才能生成一次推荐 | ① 默认全部「不详」直接生成，仅在结果中标注「因信息不足未能排查 X，建议补充」② 改分页问卷（每页 3-4 项）③ 结果页提供「补充信息后重新生成」 |
| 9 | **报告确认页支持对照原图** | 用户逐项确认 AI 抽取结果时，**看不到原报告**，无法核对；且姓名不匹配时仍默认归入当前成员 | 左右分栏：左原图（可缩放）、右抽取结果；姓名不匹配时**强制选择**目标成员 |
| 10 | **统一错误反馈** | 全仓仅 3 处 `onError/isError`。后端挂掉时首页显示「还没有成员」、设置页永久转圈；所有删除类操作失败无提示；流式失败只透出 `HTTP 429` | 统一 `ApiError` → 中文文案映射（429→「请求过于频繁」）；区分「无数据 / 加载中 / 服务异常」三态空页面；所有 mutation 补失败提示与重试 |
| 11 | **成员上下文持久化** | 实测：录入指标触发 members 刷新 → 当前成员**跳回第一个人**；刷新后永远回到第一个成员 | 选择写入 localStorage；`setMembers` 仅在当前成员失效时改选；切换成员时给 toast + 清理草稿 |
| 12 | **聊天会话管理** | 无「新建会话 / 清空 / 搜索」；历史只加载最近 50 条且**忽略 `has_more`**（后端已支持 `before_id` 分页），超出部分永久不可见且无提示 | 新建会话按钮 + 上拉加载历史 + 会话内搜索 |
| 13 | **报告缩略图与原图预览** | 报告列表缩略图 URL 硬编码 `/api/v1`，配置了 `VITE_API_BASE_URL` 后全部 404；`<img>` 无 `onError` 兜底 | 统一走 `BASE_URL` + 占位图 |
| 14 | **AI 高危提示在流式入口生效** | 流式对话只下发 `report/delta/intent`，**没有 risk 事件**；而前端只用流式——S 级拦截、A 级「建议立即就医」红色横幅**永远不会出现** | 流式补 `risk` 事件与工具调用事件 |

| # | 功能 | 产品价值 |

## 四、体验（UX）优化建议

### 4.1 移动端：先明确策略，再决定投入

**实测截图（390×844，iPhone 尺寸）**：固定 256px 侧边栏占据约 2/3 屏宽，主内容被裁切（「家庭健康速…」被截断），无汉堡菜单、无抽屉、无法折叠。**WebUI 在手机上基本不可用。**

产品层面需要先做**策略选择**，而不是无脑做响应式：

- **方案 A（推荐）**：承认「移动 = 飞书」，WebUI 只保证**最小可用**（侧栏可折叠 + 表格可横向滚动 + 关键操作可点），把移动端体验投入放到飞书（配合建议 1 的主动推送，飞书自然成为移动主入口）
- **方案 B**：全面做 WebUI 响应式（<768px 抽屉式导航 + 底部 Tab），投入大，但适合「不想装飞书」的用户

无论哪个方案，**建议先把「双入口」在 UI 上说清楚**：飞书渠道页加一句「日常在飞书随手记录，WebUI 用于深度管理」，并在移动端 WebUI 顶部提供「在飞书中继续」入口。

### 4.2 具体交互改进

| 问题 | 现状 | 建议 |
|---|---|---|
| **Dashboard 信息过载** | 单页 9 个卡片区平铺（危急值/待办/基础信息/指标/异常项/6 类病史/汇总），无折叠、无锚点导航 | 病史区默认折叠 + 顶部锚点导航；危急值/待办置顶 |
| **免责声明冗余** | 每条 AI 消息都重复一遍免责声明 | 改为会话级常驻一条（侧栏或输入框上方） |
| **危险操作保护不均衡** | 删除成员有二次确认 ✅；删除报告/飞书渠道用原生 `confirm()`；「清除全部数据」两次点击即执行、且与导出按钮无联动 | 统一确认组件；清除数据需**输入 DELETE**；提供「先导出再清除」的一键路径 |
| **加载态缺失** | 首页成员卡无 loading，数字先显示 0 再跳变（N 个成员 × 3 个接口的扇出请求） | 骨架屏 + 后端聚合接口（一次返回全家速览） |
| **日期格式四套并存** | `2024/05/01`（报告）、`2024年5月1日`（指标视图）、`5/1 14:30`（录入）、`toLocaleDateString()`（看板） | 抽统一 date util |
| **指标单位两处维护** | 前端 `METRIC_LABELS` 与后端 `unit` 各写一份，可能不一致 | 单位以后端返回为准 |

### 4.3 可访问性（A11y）

实测全仓 **0 个** `aria-*` / `role="dialog"`。具体问题：

- **对比度不达标**：`text-slate-400` (#94A3B8) 白底约 **2.6:1**；用户气泡内时间戳 `#99B3FF` on `#3363FF` 约 **2.3:1**——均低于 WCAG AA 的 4.5:1
- **弹窗无焦点管理**：无焦点陷阱、无 Esc 关闭、打开后焦点不进入（5 个弹窗全覆盖）
- **键盘不可达**：报告确认弹窗的勾选行是 `div + onClick`（无 `aria-checked`），键盘用户无法操作
- **图表仅靠颜色**区分正常/异常（色觉障碍用户不可用）

对一个面向**全家庭（含长辈）**的健康产品，可访问性的优先级应该高于一般产品——长辈往往需要更大字号与更高对比度。建议至少：把次要文字提到 `slate-500/600`、弹窗加焦点管理与 Esc、把 `div+onClick` 换成真 `<input type="checkbox">`。

## 五、建议的功能路线图

### V1.3「让管家开口说话」（建议主题：闭环 + 触达）

### V1.4「让人愿意录入」（建议主题：降低摩擦）
6. 首次使用引导向导

## 六、一句话总结

**这个产品的医学专业度、架构设计（provider 可插拔、渠道抽象、画像单一事实来源）和成本意识都在开源同类项目之上，真正的短板不是「少功能」，而是「已有价值没有被交付到用户手上」**：

> 报告解析成功了，但用户看不到变化；
> 待办生成了，但不会提醒；
> 危急值入库了，但没有被判危急；
> 有告警，但只增不减直到被无视。

把这三条「最后一公里」接通——**主动推送、入档闭环、告警生命周期**——产品的完成度会有质的变化。其中「飞书主动推送」的成本最低、感知最强，建议作为下一个版本的头号功能。
